# 7. API, User Interface and Deployment

## 7.1 Introduction

PathSnap provides a web-based interface for submitting trips and viewing reconstructed routes. The backend is implemented using FastAPI, while the prediction pipeline connects the data-processing, candidate-generation, machine-learning and route-reconstruction components.

The system was designed to run across two laptops connected through a local network:

- **Laptop 1:** Runs the FastAPI backend and trained prediction pipeline.
- **Laptop 2:** Runs the evaluation user interface and communicates with the backend through HTTP requests.

This architecture separates model execution from the user interface and demonstrates how the trained model can be accessed as an application.

## 7.2 System Architecture

The application follows this sequence:

1. The user selects a trip through the user interface.
2. The interface sends a request to the FastAPI backend.
3. The backend loads the requested trip.
4. The prediction pipeline hides the reference route.
5. Candidate road segments are generated for GPS observations.
6. The trained Random Forest model assigns matching probabilities.
7. The HMM and Viterbi decoder reconstruct the route.
8. The backend returns GPS coordinates, predictions, the reconstructed route and available evaluation metrics.
9. The user interface displays the results.

The backend is implemented in `api/main.py`, while the processing workflow is implemented in `api/pipeline.py`.

## 7.3 FastAPI Backend

FastAPI was selected to expose the prediction pipeline through HTTP endpoints.

The application is created with the title `PathSnap API`.

The backend provides three main endpoints.

| Endpoint | Method | Purpose |
|---|---|---|
| `/health` | GET | Checks whether the API is running |
| `/trips` | GET | Returns available trip IDs |
| `/predict` | POST | Runs the complete prediction pipeline for a selected trip |

### Health Endpoint

The `/health` endpoint returns:

```json
{
  "status": "ok"
}
```

This endpoint helps verify that the backend is operational.

### Trips Endpoint

The `/trips` endpoint returns the available trip IDs from the configured evaluation folder.

The user interface uses this endpoint to obtain the list of trips that can be selected for prediction.

### Predict Endpoint

The `/predict` endpoint accepts a JSON request containing a trip ID.

Example request:

```json
{
  "trip_id": "00000056"
}
```

The backend validates the trip ID and confirms that the requested trip exists in the evaluation folder. Unknown or invalid trip IDs receive an HTTP 404 response.

For a valid trip, the backend executes the complete PathSnap prediction pipeline.

## 7.4 Prediction Pipeline

The `Pipeline` class in `api/pipeline.py` connects the different project modules.

The prediction process follows these stages:

**Stage 1 — Load the trip**

The loader reads the GPS observations and associated road-network data.

**Stage 2 — Hide the reference route**

The original reference route is retained separately for later evaluation. A copy of the trip with `route=None` is created for prediction.

**Stage 3 — Generate candidates**

The candidate-generation module identifies nearby directed road segments for each GPS observation.

**Stage 4 — Score candidates**

The trained Random Forest model assigns a matching probability (`p_match`) to each candidate.

Reference labels and reference arc columns are explicitly excluded from the model-scoring input.

**Stage 5 — Decode the route**

The HMM and Viterbi decoder use candidate probabilities and road-network transitions to select the predicted road segment sequence.

**Stage 6 — Evaluate predictions**

Only after prediction is complete does the backend use the reference route to calculate evaluation metrics, where reference data is available.

**Stage 7 — Prepare the response**

The backend converts the predicted road-segment sequence into geographical coordinates and prepares the response for the user interface.

## 7.5 API Response Structure

The prediction endpoint returns the following main fields:

| Field | Description |
|---|---|
| `trip_id` | Identifier of the selected trip |
| `gps` | Original GPS coordinates in latitude-longitude order |
| `predicted` | Predicted arc ID for each GPS observation |
| `route` | Reconstructed route as latitude-longitude coordinates |
| `metrics` | Available prediction and evaluation metrics |

The `predicted` array contains one prediction entry per GPS observation. An arc ID of `-1` indicates that no road segment was assigned to that observation.

The route is generated by converting the selected road arcs into a geographical polyline.

The API does not return the reference route, reference arc labels or ground-truth information.

## 7.6 Prevention of Ground-Truth Leakage

An important design consideration is ensuring that the model does not receive the correct route while making predictions.

PathSnap addresses this through the `without_route()` operation.

The prediction pipeline:

- Loads the original trip.
- Stores the reference route separately.
- Creates a copy with the reference route removed.
- Generates candidates using the route-hidden copy.
- Scores candidates using the trained model.
- Runs Viterbi decoding using the route-hidden copy.
- Uses the original reference only after prediction to calculate metrics.

This ensures that the model's predictions are based on GPS observations and road-network information rather than the known answer.

## 7.7 Two-Laptop Deployment

The application was tested using two laptops connected through a mobile hotspot.

**Laptop 1 — Backend**

The FastAPI application and trained prediction pipeline run on the first laptop.

The backend is started using:

```bash
uvicorn api.main:app --host 0.0.0.0 --port 8000
```

The `0.0.0.0` host setting allows other devices on the same network to access the API.

**Laptop 2 — User Interface**

The second laptop runs the evaluation interface in a browser.

It sends HTTP requests to the backend using the first laptop's local network IP address.

Because the interface and API run on different devices, Cross-Origin Resource Sharing (CORS) middleware is configured in FastAPI to allow browser requests.

The API also exposes the `X-PathSnap-Pipeline` response header, which identifies whether the trained or placeholder pipeline is being used.

## 7.8 Startup and Model Warm-Up

During application startup, the backend:

1. Loads the prediction pipeline.
2. Identifies the available evaluation trips.
3. Loads the model and configuration files.
4. Loads the HMM decoder configuration.
5. Performs a warm-up operation by scoring a small number of candidates.

The warm-up operation helps load the trained model before the first user prediction request.

The API also logs request details, response status codes, execution time, prediction timings and available evaluation metrics.

## 7.10 Conclusion

The FastAPI backend and user interface provide an operational application around the PathSnap machine-learning pipeline.

The backend connects candidate generation, Random Forest scoring and HMM-based route reconstruction through a single prediction workflow.

The two-laptop deployment demonstrates that the model can be accessed remotely through an HTTP API. Automated testing and ground-truth separation checks provide additional confidence in the correctness and integrity of the application.
